The [distance sensor](../distance-sensor/#what-it-cant-tell-you) can tell you something is 150 mm ahead. It can't tell you whether that something is red. Plenty of games hand you pieces of two colors and want only one of them, so the intake has to carry a red piece in and send a blue one back out, with nobody touching a button.

The V5 Optical Sensor answers the question the other sensors can't: what color is the thing in front of me. The running robot has one on port 12, named `colorSensor`, mounted where pieces pass on the way into the `intake`.

## Color from reflected light

An object has a color because of which light it bounces back. A red piece reflects mostly red light and soaks up much of the rest. The sensor shines its own LED at the piece and measures what comes back, so it doesn't depend only on the room. You control the LED with <Api sym="optical/set_led_pwm" />, which takes a brightness from 0 to 100. The light that was already there, from ceiling lamps and windows, is <Term id="ambient-light">ambient light</Term>. It adds to what the sensor sees and changes from one venue to the next, and it is a common reason a color reading that worked at home fails at a competition. That's reasoning, so test it in your venue.

What comes out is three numbers, the amounts of red, green and blue. That's <Term id="rgb">RGB</Term>, and <Api sym="optical/get_rgb" /> returns it, along with a brightness value as a fourth field. The raw version, <Api sym="optical/get_raw" />, gives whole-number red, green and blue counts plus a `clear` value.

RGB is awkward for deciding "is this red". A red piece under a bright light might read 200 red, 30 green, 30 blue, and the same piece in shade 100, 15, 15. All three numbers moved, though the color didn't change. Your check would need a rule about the ratios, not the numbers.

## Hue, saturation and brightness

There's a second way to write the same color that separates what you care about from what you don't. It splits a color into three numbers:

- <Term id="hue">Hue</Term> is the color itself, as an angle around a color wheel. In the standard hue scale, 0 is red, about 120 is green and about 240 is blue, then it comes back around to red. <Api sym="optical/get_hue" /> returns 0 up to just under 360.
- <Term id="saturation-color">Saturation</Term> is how strong the color is, from 0 (gray) to 1 (vivid). <Api sym="optical/get_saturation" /> returns it.
- Brightness is how much light, from 0 to 1. <Api sym="optical/get_brightness" /> returns it.

Light and shade mostly change brightness. A red piece stays near the same hue in both. That's why sorting code reads hue and uses the other two to decide whether to trust it. A gray tile has almost no saturation, so its hue is nearly meaningless, and a sorter that doesn't check saturation will react to a gray tile as if it were a colored piece.

Hue is an angle, so it has the same problem as the inertial sensor's heading. It loops, which is <T id="wraparound">wraparound</T> again. Red sits on both sides of 0: a slightly orange red reads 5, and a slightly pink red reads 350. BLRS's wiki puts the red band at roughly 340 to 20, and VEX's own docs list color bands. Both are starting points, not a spec for your field, so the band in this scene is an example.

Write what looks natural for red and you get

```cpp nocheck
bool isRed(double hue) {
    return hue > 340.0 && hue < 20.0;  // never true
}
```

No number is greater than 340 and less than 20 at once, so this returns false for every hue, including a perfect red. The code compiles and runs. It just never sorts anything. The fix is the same idea as `shortestTurn` on the inertial sensor page, [wraparound and the shortest turn](../inertial-sensor/#wraparound-and-the-shortest-turn): the scale loops, so a band that crosses the seam is two pieces, one at each end. A hue is red if it's high enough or low enough.

```cpp
// Example band. Measure your own pieces under your own lights
bool isRed(double hue) {
    return hue > 340.0 || hue < 20.0;
}
```

The rule that goes with it: if the band crosses 0, the start is bigger than the end and you join the tests with `||`. If it doesn't, such as blue, you join them with `&&`. The scene checks which is right for whatever band you set, and shows what happens if you use the wrong one.

## Reading it in code

The sensor is a <Api sym="optical/Optical" />, the `colorSensor` object, so there's nothing to declare. Turn the LED on in `initialize()`, and print what it sees. [Printing a value to the Brain screen](../../first-robot-program/inside-a-pros-project/#printing-a-value-to-the-brain-screen) covers `lcd::print`.

```cpp
void initialize() {
    pros::lcd::initialize();

    colorSensor.set_led_pwm(100);
}

void opcontrol() {
    while(true) {
        pros::lcd::print(0, "hue: %.1f", colorSensor.get_hue());
        pros::lcd::print(1, "saturation: %.2f", colorSensor.get_saturation());
        pros::lcd::print(2, "brightness: %.2f", colorSensor.get_brightness());

        pros::delay(10);
    }
}
```

Like the other sensors, a failed read gives an error value. For these doubles it's `PROS_ERR_F`, which is infinity, set with <T id="errno">`errno`</T>, the pattern from [when the sensor isn't there](../why-sensors/#when-the-sensor-isnt-there). Infinity is greater than 340, so a careless `isRed` would call a disconnected sensor red. The sorter below checks for it.

Now do the measurement that the whole page depends on. Hold each game piece in front of the sensor where it will pass on the robot and write down the hue range you see, then do the same in other lighting. The ranges come from your pieces, your sensor and your venue. Numbers in this page are examples and won't be your numbers.

## Proximity

Hue is only trustworthy when a piece is actually there and close. <Api sym="optical/get_proximity" /> returns 0 to 255, and BLRS says higher means closer. It's a <Term id="proximity-sensor">proximity sensor</Term>, which means it tells you roughly how close without giving a distance in real units. That's the difference from the distance sensor's millimeters. How strong the return is also depends on how reflective the surface is, so the same number can mean different distances for different pieces. That's reasoning from how reflection works, so test it. BLRS also says color detection works best closer than 100 mm.

Use proximity as a gate. Only believe the hue when the proximity is above a threshold, and find the threshold the way you found the hue: print it with and without a piece in place.

## Integration time and speed

The sensor doesn't see an instant. It collects light for a while and then reports what it gathered. That collecting time is its **integration time**, and it works like the exposure time of a camera: longer collects more light and gives a steadier reading, shorter reacts faster.

<Api sym="optical/set_integration_time" /> sets it in milliseconds from 3 to 712, and <Api sym="optical/get_integration_time" /> reads it back. The header says the default is 100 ms and that the sensor sends the Brain a new value every 20 ms. Together those suggest a reading at the default reflects roughly the last 100 ms of light, a window that slides forward in 20 ms steps. The header doesn't spell out the averaging, so the scene below is that reading of it, a simplified model, not a measured one.

If a piece is in view for less time than the window is long, no reading ever sees it alone. Every reading blends the piece with the background before and after it. And a faster intake gives a piece less time. Think of an intake belt moving a 2 inch piece past the sensor at 30 inches per second: it's in view for about 67 ms.

<Scene name="sensors/sample-window">
A 2 inch piece passes the sensor. The speed and the 2 inch length are illustrative, and so is "in view for the piece's length divided by its speed". Each blue tick is a reading, as tall as the share of its window that had the piece in it. At the default 100 ms and 30 in/s, no reading is more than about two-thirds piece. Slide the integration time down below the in-view time and the best reading can reach 100%. Then push the speed up and the window has to shrink again. At 120 in/s and 3 ms, readings every 20 ms can fall entirely between the piece's edges and never see it, so a short window needs a slow piece or a lucky tick.
</Scene>

The cost of a short window is less light per reading, which likely means more <T id="noise">noise</T>, especially in dim light. That's the general trade for any sensor that collects over time, not a figure from VEX. The sensible procedure is to set the integration time to roughly the shortest in-view time you expect or a bit less, print hue for a piece that passes, and widen it if the readings jump around.

## Sorting by color

Now all the parts can work together. The loop below runs the `intake` forward, watches for a piece, and runs the intake in reverse for a moment when the piece is the wrong color. How a mechanism sends a piece away depends on its design, and reversing the intake is the simplest, so that's what this does. The band, the saturation floor and the proximity threshold are all examples. Replace them with numbers you measured.

```cpp withprev
// Examples only. Measure these on your own field
const int NEAR_PROXIMITY = 150;
const double MIN_SATURATION = 0.4;
const int REJECT_MS = 300;

// Keeps red pieces, spits back out anything else
void sortIntake(int milliseconds) {
    int rejectLeft = 0;

    for(int elapsed = 0; elapsed < milliseconds; elapsed += 10) {
        double hue = colorSensor.get_hue();
        double saturation = colorSensor.get_saturation();
        int proximity = colorSensor.get_proximity();

        // A failed read must never look like a piece
        if(std::isinf(hue) || std::isinf(saturation) || proximity == PROS_ERR) {
            intake.move_voltage(12000);
            pros::delay(10);

            continue;
        }

        bool piecePresent = proximity > NEAR_PROXIMITY && saturation > MIN_SATURATION;

        if(piecePresent && !isRed(hue)) {
            rejectLeft = REJECT_MS;
        }

        if(rejectLeft > 0) {
            intake.move_voltage(-12000);
            rejectLeft -= 10;
        } else {
            intake.move_voltage(12000);
        }

        pros::delay(10);
    }

    intake.move_voltage(0);
}
```

Call `sortIntake(5000)` in `autonomous()` to run it for five seconds. The `for` loop adds 10 each time around, matching the `pros::delay(10)` that [every loop needs](../../first-robot-program/driver-control/#why-the-loop-has-a-delay), so `elapsed` counts roughly milliseconds. The `isRed` function from earlier has to sit above it in the file.

Read the loop as three questions in order: did the read work (if not, it keeps intaking and skips the sorting), is there a piece I can believe, and is it the wrong color. The `rejectLeft` counter keeps the intake in reverse for 300 ms after the last bad piece, since one 10 ms tick of reversing wouldn't clear anything.

It's a simple version, with weaknesses you'll find on the robot. A piece whose hue sits on the edge of a band can flip between kept and rejected from one reading to the next. A piece that moves faster than the integration window blends with the background, as the last scene showed. And the reversal starts late by about the sensor's window. Fixes for the first of those get a name in Feedback Control, since it's the same chatter a robot has around a target.

## Gestures

The sensor has one more trick: it can tell which way something moved across it. Turn it on with <Api sym="optical/enable_gesture" /> and read <Api sym="optical/get_gesture" />, which returns a code: 0 for none, 1 for up (toward the cable), 2 down, 3 right and 4 left. The header says a gesture is cleared after 500 ms. This is <Term id="gesture-detection">gesture detection</Term>. A hand wave could trigger something, say.

It costs you color. While gestures are on, hue, saturation, brightness and proximity aren't available, so a sorter can't use both at once. Switch it off with <Api sym="optical/disable_gesture" /> to get color back.

## What to do with the numbers

You can read what the robot's motors, shafts, heading, wall distance and piece colors are doing now, and every example in this section did something blunt with the number: an `if` and a fixed voltage. Those are the programs that overshoot, coast and chatter. What a robot does with a measurement so that it arrives where it should, without a person steering, is the next section, starting at [Why Control Theory Matters](../../feedback-control/why-control-theory/).

<Check prompt="A green piece reads a hue between 100 and 140. Which of `hue > 100.0 && hue < 140.0` and `hue > 100.0 || hue < 140.0` is right, and what would the wrong one do?">
The `&&` one. The band doesn't cross 0, so a hue has to be above 100 and below 140 at once. With `||`, every hue passes, since any number is either above 100 or below 140, so every piece would count as green.
</Check>

<Check prompt="The sorter reads a steady hue of 30 and a proximity of 20 from the empty belt with the floor in view. Why doesn't it reject that as a wrong-colored piece?">
Proximity 20 is below `NEAR_PROXIMITY`, so `piecePresent` is false. The hue of a far or empty scene isn't a piece's color, so the code only trusts the hue when something is close and vivid.
</Check>

<Check prompt="Pieces pass at 60 in/s and are 2 inches long, with the default integration time. What's the problem, and what would you change?">
2 inches at 60 in/s is about 33 ms in view, but the default window is about 100 ms, so every reading is mostly background. Lower the integration time with `set_integration_time` to around 30 ms or less, then print hue as a piece passes to see how noisy it gets, and widen the window a little if so. Slowing the intake also helps.
</Check>
